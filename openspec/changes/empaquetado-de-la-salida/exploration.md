## Current State

### `app/core/tipos.py` — `ArchivoSalida` (lines 29-35)
`@dataclass(frozen=True, slots=True)` with exactly three fields: `nombre_propuesto: str`, `ruta_temporal: Path`, `tipo_mime: str`. Always a path already on disk — no bytes-vs-path ambiguity, no size field. This is the only currency type packaging will consume/produce.

### `app/core/errores.py` — closed 5-type `TipoError` enum
`FORMATO`, `TAMANO`, `CONTENIDO`, `CANTIDAD`, `CLAVE_INEXISTENTE` (lines 32-39). `_ESTADO_HTTP` maps all four correctable types to 422 and `CLAVE_INEXISTENTE` to 500 (ADR 0018). `ErrorContenido` (lines 184-204) has `contexto: ContextoContenido = {archivo: str, motivo: Literal["columna_faltante", "cero_filas"], columna: str | None}`. **`"cero_filas"` already exists in the codebase**, but it was minted in item #3 for `Contado_Carga`'s domain semantics ("no valid rows in the source data" — item #16, not yet built), not generically for "a processor's `procesar()` returned an empty list." Whether item #9 reuses this motivo or needs a new one is an open question (see below). `ErrorTipificado.__reduce__` (lines 122-133) guarantees pickling across the `Pipe` — already covers any error packaging raises, no new work needed there.

### `app/core/temporales.py` — ownership/cleanup model (ADR 0020)
Single-transfer-point model: `Reserva` owns a per-request directory (`mkdtemp(prefix="pet-", dir=raiz())`), cleans in `finally` unless `ceder_limpieza()` transfers ownership to a `BackgroundTask` on the response. `preparar_raiz()`/barrendero (age + `_EN_VUELO` double condition) already handle orphan cleanup. Nothing here needs to change for item #9 — whatever packaging produces must live inside a `Reserva`-tracked directory so the existing cleanup machinery (background task + sweeper) covers it "for free." ADR 0020 explicitly names "el ZIP intermedio" as one of the temporals that must not survive the response.

### `app/recepcion.py` — the literal seam
Ends at `raise NotImplementedError` (line 190) with an explicit comment: *"Costura de los ítems #9/#10 -- el único cambio que necesitan acá: `return FileResponse(salida, background=reserva.ceder_limpieza())`"* (lines 188-189). The route docstring (lines 134-135) says the same thing again. This confirms the intended integration shape at the HTTP edge: a single `FileResponse`-like construction fed by whatever comes out of packaging, using `reserva.ceder_limpieza()` for cleanup transfer — but item #9 itself does **not** touch `recepcion.py`; that wiring is item #10's job (pipeline steps 0-9). Also confirms `_copiar` (lines 62-102) is explicitly designed to be reused by items #9/#10 ("no deben poder excederse por olvidar la comprobación previa" — a bounded writer already exists as precedent for writing the ZIP itself).

### `app/registry.py`, `app/core/contrato.py`
`REGISTRY: dict[str, Procesador] = {}` — empty. `ContratoProcesador` has no packaging-related fields (no output-size ceiling, no output-count limit). `obtener_contrato` always returns `None` today (`_TABLA_CONTRATOS` empty), so no processor exists to exercise packaging end-to-end yet — item #9 must be testable standalone, against hand-built `list[ArchivoSalida]`, exactly like `validaciones.py` is testable against hand-built `ContratoProcesador`.

### `app/core/validaciones.py`
`PRESUPUESTO_DE_RAM_BYTES = 256 * 1024 * 1024` (line 32) — governs **declared uncompressed input** size (anti zip-bomb on uploads), checked via `ZipFile.infolist()` metadata only, no decompression. This precedent exists on the input side; nothing equivalent exists for **output** ZIP construction or aggregate output size.

### `app/core/ejecucion.py` (item #8, shipped — ADR 0022) — the real upstream caller
`ejecutar_modulo(*, clave: str, entradas: list[ArchivoEntrada], timeout: timedelta) -> list[ArchivoSalida]` (lines 364-385) is the function that will hand packaging its input, once item #10 wires the pipeline. It already:
- Re-raises `ErrorTipificado` verbatim if the child raised one (`ErrorDelHijo`).
- Raises `FalloDelModulo`/`EjecucionExpirada`/`HijoMuerto` for non-typed process failures — **all explicitly NOT `TipoError`**, and ADR 0022 explicitly defers their HTTP translation to item #10, not to packaging.
- Returns `list[ArchivoSalida]` only on the clean success path (`SalidaDelHijo`).

This means packaging **never needs to handle partial/anomalous module outcomes** — by the time `archivos: list[ArchivoSalida]` reaches packaging, `procesar()` already either fully succeeded (this exact list, atomically produced inside one child process call) or the pipeline never calls packaging at all (an exception already propagated). The "no ZIP a medias" concern from BACKLOG is therefore **already mostly satisfied upstream**; the remaining atomicity surface specific to item #9 is the ZIP-*writing* step itself (disk full, permission error while `zipfile.ZipFile` writes), not the module's output being incomplete.

## The Seam

TECH-DESIGN.md's architecture diagram (lines 62-82) and ADR 0011 (lines 27-50) both name the target module explicitly: **`app/core/empaquetado.py`**, sibling to `validaciones.py`, `errores.py`, `temporales.py`, `ejecucion.py` inside `core/`. Both documents also state the module's one-line job: *"ZIP si hay más de una salida."*

Recommended shape (to confirm in design phase, not decided here): a pure-ish function taking `archivos: list[ArchivoSalida]` and a target directory (the caller's `Reserva.directorio`, so the ZIP lands inside the same lifecycle-tracked location) and returning a single `ArchivoSalida` — either the sole input verbatim (1 output) or a synthesized one pointing at a newly-written `.zip` file (N outputs), so the HTTP edge (item #10) can construct exactly one `FileResponse(salida.ruta_temporal, media_type=salida.tipo_mime, filename=salida.nombre_propuesto, background=reserva.ceder_limpieza())` regardless of cardinality. Zero outputs must raise an `ErrorTipificado` (`ErrorContenido`, see hard question 4) before writing anything. This keeps `ArchivoSalida` as the single currency type crossing every internal boundary in `core/`, consistent with how `ArchivoEntrada`/`ArchivoSalida` are already the only types crossing the process boundary (ADR 0012/0022).

Alternative shapes exist (e.g. packaging returning a `Response` directly, or a `(Path, str, str)` tuple) — surfaced, not decided; the `ArchivoSalida`-in/`ArchivoSalida`-out shape is a recommendation, not a foregone conclusion, since it hasn't been tested against how item #10 will actually assemble the pipeline.

## Constraints Sourced From Authoritative Docs

- **TECH-DESIGN.md line 102**: "Empaqueta: una salida se entrega tal cual; más de una se comprime en ZIP" — runs as **pipeline step 8, in the parent process** (only step 7, module execution, crosses to the child).
- **TECH-DESIGN.md lines 210-214 (acceptance criteria)**: ZIP contains exactly the returned files with their names, **"sin rutas absolutas ni componentes de directorio embebidos"** (flat archive). Neither the individual output files nor "el ZIP intermedio" survive the response.
- **PRD.md lines 286-290**: zero outputs "no es un error del sistema, pero el portal necesita distinguirlo del éxito normal: debe llegar como error de contenido, no como ZIP vacío." Partial multi-file generation ("genera el primer archivo pero falla al generar el segundo") must never produce a half ZIP — "o sale la salida completa, o es un error."
- **ADR 0020**: single-transfer-point ownership model; `FileResponse`/`StreamingResponse` both call `background()` only *after* the send loop, so a client disconnect mid-stream already skips ceded cleanup regardless of response class chosen — the sweeper (15 min age threshold) is the real backstop, not the response class.
- **ADR 0021**: `PRESUPUESTO_DE_RAM_BYTES = 256 MB` precedent for input-side RAM ceilings, declared as a module-level `Final` with a documented rationale (not a `ContratoProcesador` field) — same pattern would likely apply to any new output-side ceiling. Also establishes the precedent of growing the `Contexto` union (`ContextoTamanoTotal` sibling to `ContextoTamano`) without reopening the closed `TipoError` enum, for batch-level errors that have no single culprit file.
- **ADR 0022**: `FalloDelModulo`/`EjecucionExpirada`/`HijoMuerto` translation to HTTP is explicitly item #10's job, not item #9's or #8's. Confirms packaging's scope is narrowly the happy-path `list[ArchivoSalida]` plus its own zero-output check.
- **openspec/config.yaml:8** confirms the stale comment noted in the task ("0011-0015 exist") — actual range is 0011-0022 (12 files), already flagged once before by ADR 0022's own context section. Re-verified for this change: the next free ADR number is **0023**.
- No existing text anywhere in TECH-DESIGN.md/PRD.md/REVISION-ADVERSARIAL.md mentions `Content-Disposition`, streaming vs in-memory ZIP, or compression-level/determinism — these are genuinely open, not just unread.

## Hard Questions (surfaced, not decided)

1. **In-memory ZIP vs temp file.** ADR 0020 explicitly names "el ZIP intermedio" as a temporal that must be cleaned, and the existing lifecycle machinery (`Reserva`/sweeper) is disk-based — both point toward writing the ZIP to a temp file inside `reserva.directorio` rather than building it in an `io.BytesIO`. Against that: no output-size ceiling exists yet (unlike `PRESUPUESTO_DE_RAM_BYTES` for inputs), so an in-memory approach isn't obviously unsafe for currently-contracted output sizes either. This needs an explicit decision plus, if temp-file, whether it reuses `_copiar`'s bounded-write pattern from `recepcion.py`.
2. **What "nunca sale un ZIP a medias" means mechanically.** Given item #8 already guarantees `procesar()`'s output is all-or-nothing before packaging ever runs, the remaining atomicity concern is: the ZIP file itself must be fully written and `close()`d (all entries flushed, no `BadZipFile` truncation) *before* any `Response` object is constructed — never assemble/stream ZIP bytes directly into the response body. Whether the eventual response uses `FileResponse` on a completed file (recommended, matches ADR 0020's own analysis of both response classes) or something else is item #10's call, but item #9's contract should be: package fully to a real file first, raise before returning if the write fails, never return a handle to a partially-written file.
3. **Naming/collisions inside the ZIP.** `ArchivoSalida.nombre_propuesto` is set by trusted first-party module code (not client input), unlike `ArchivoEntrada.nombre_original` (client-controlled, deliberately never used to construct a path per ADR 0020). Should packaging trust `nombre_propuesto` verbatim as the zip `arcname`, or defensively flatten it (strip any separators/`..`) as defense-in-depth, consistent with ADR 0020's broader principle that no name ever derived from outside `core/`'s own control is trusted for path construction? Duplicate `nombre_propuesto` values across a single `procesar()` call's outputs also need an explicit policy (silent last-write-wins in `zipfile`, or an error) — undecided today.
4. **Which error type covers "cero salidas" and its exact shape.** BACKLOG assigns this to `TipoError.CONTENIDO` (422, not 500 — confirmed by `_ESTADO_HTTP`). But `ContextoContenido` requires `archivo: str` and a closed `motivo: Literal["columna_faltante", "cero_filas"]`. Two sub-questions: (a) does packaging reuse `motivo="cero_filas"` even though that value's existing semantics are row-level (Contado_Carga, item #16), not "the module returned nothing at all" — a generic passthrough-style processor returning zero outputs isn't about "filas"; or does it need a new `motivo` value, which is a direct edit to a closed `Literal` (not the union-growth pattern ADR 0021 used for `ContextoTamanoTotal`, since `motivo` is a scalar field, not the `Contexto` union itself); (b) what `archivo` value applies when the zero-output fact is module/batch-level with no single input file responsible — mirrors the `ErrorTamano.total()` precedent (a sibling shape without a culprit), which could argue for a similar `ErrorContenido` classmethod/shape rather than forcing an arbitrary `archivo` string.
5. **`Content-Disposition`/filename encoding for non-ASCII names.** No precedent exists anywhere in the repo (confirmed by search) — `nombre_propuesto` values are module-controlled, so non-ASCII is plausible (self-inflicted, not adversarial) but Starlette's default `Content-Disposition` header construction needs an explicit decision on RFC 5987/6266 (`filename*=UTF-8''...`) encoding, especially for the ZIP archive's own outer filename.
6. **`ZIP_DEFLATED` vs `ZIP_STORED`, fixed timestamps/determinism.** Nothing in PRD/TECH-DESIGN mandates a compression choice. ADR 0015 mandates byte-for-byte parity for individual TXT/Excel outputs (item #15/#16 fixtures) but says nothing about whether a future ZIP *container* (once `Contado_Carga` or another processor emits 2+ files) must itself be byte-reproducible. If any future parity fixture ever hash-compares a ZIP wholesale rather than its unpacked contents, `ZIP_DEFLATED`'s timestamp/host-OS/version metadata fields make output non-deterministic across machines unless pinned (`ZipInfo.date_time`, `external_attr`, `compress_type`) — speculative today, flagged for awareness, not for a decision in this item.

## Existing Patterns To Follow

- **Module docstring convention**: opens with backlog item + governing ADR references, states the "why" in terms of REVISION-ADVERSARIAL findings (H-04, H-09, etc.) where relevant, and explicitly states the `core/` → `procesadores/` non-import invariant (`app/core/temporales.py:1-12`, `app/core/validaciones.py:1-21`, `app/core/errores.py:1-18`).
- `from __future__ import annotations` at the top of every `core/` module.
- Multi-argument constructors are keyword-only (`ErrorFormato.__init__(self, *, archivo:, ...)` in `errores.py:140-142`; every function in `validaciones.py`).
- Pure functions over primitives, never Starlette types crossing into `core/` — explicit rule stated in `validaciones.py:10-14` ("Reciben primitivos... nunca un `UploadFile`"). Packaging should follow the same rule: it should never see `UploadFile`/`Request`/`Response`, only `ArchivoSalida`/`Path`.
- `Final` module-level constants get long rationale docstrings (`temporales.py` `UMBRAL_DE_EDAD`/`INTERVALO_DE_BARRIDO`, `validaciones.py` `PRESUPUESTO_DE_RAM_BYTES`) — any new output-side constant packaging introduces should follow the same documented-constant pattern rather than becoming a `ContratoProcesador` field (ADR 0021 explicitly rejected adding memory-budget fields to that dataclass).
- Tests live in `tests/test_<modulo>.py`, Spanish behavioural test names (`test_no_quedan_temporales_tras_una_respuesta_completa`), grouped into scenario classes (`TestRechazoAntesDeEscribir`, `TestBombaZipEnLaFaseDos` in `test_recepcion.py`), reusing `conftest.py` fixtures (`token_sentinela`, `limpiar_cache_configuracion`).
- mypy strict typing throughout: frozen/slots dataclasses, `ClassVar` for the `tipo` discriminant, closed `Literal`/`TypedDict` unions for `contexto` shapes.

## Test Surface

Recommended behavioural tests for item #9 (exact names/module TBD in design phase):
- A single `ArchivoSalida` passed in comes back unchanged (verbatim path/MIME/name), no ZIP produced.
- Two or more `ArchivoSalida`s produce exactly one ZIP containing those files under those names, with no directory components in any `arcname` (flat archive — proves "sin rutas embebidas").
- Zero `ArchivoSalida`s raises `ErrorTipificado` (whichever `ErrorContenido` shape the design phase settles on) before any ZIP file is created on disk.
- Duplicate `nombre_propuesto` values across outputs — behavior depends on the collision-policy decision above; needs an explicit test once decided.
- A hostile/path-like `nombre_propuesto` (defense-in-depth) is confined to a flat, safe `arcname`.
- Simulated write failure mid-ZIP-construction (mocked `zipfile` write raising) leaves no partial `.zip` file visible/returned, and packaging's own directory stays clean or the caller's cleanup still fires — the "never half a ZIP" guarantee, exercised directly rather than only argued from upstream atomicity.
- (Once item #10 wires the HTTP edge) an integration-level test that the ZIP/output file does not survive the response — likely belongs to item #10's own suite, but a standalone item #9 test can already assert packaging writes only inside the given directory and returns a `Path` that exists at return time.
